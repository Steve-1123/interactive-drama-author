# 从文字故事到互动剧

## 输入与内部阶段

先保留原稿并说明改编边界。一个大纲无需预分章集，但要能识别人物动机、核心冲突、转折和结局；信息不足可以提出明确假设，不能把新增情节假称原作内容。

1. **数量与骨架**：需要精确数量校验时，在临时目录用 `--plan` 展开请求。分配稳定键、章主题、每集叙事目标、集出口和结局；为不同玩家路径准备汇合条件。预算不可实现时解释冲突，不擅自扩篇。
2. **角色与资产初规划**：统一人物描述、时空、服装/道具连续性和风格；选择有限状态变量及其叙事含义。剧/章/集asset_refs仅组织资料，不替代实际单元引用。
3. **分集细化**：写单元意图、场景描述、台词和选择。新增选择必须解释玩家意图与后果；避免看似两项却没有任何叙事差异。不会影响数值的选项也可以影响路线和叙述，不强制每项都加分。
4. **资产反查**：遍历所有单元，包括支线和结局，补素材需求及生成prompt，合并真正相同的需求。特殊状态不能被“节省成本”错误合并。
5. **机器检查与修复**：运行validate.py。优先解决Schema/引用，再图/状态，再预算；最多三轮。修复不得超出用户授权范围。被错误报告引用的field_path指向具体实体。
6. **交付说明**：在回复中记录机器覆盖范围、原稿到改编差异、选择意义、汇合风险和资产计划；不额外生成说明文件。

长剧可以分章/集处理，但阶段结果只放临时目录。生成一集只需全剧骨架、人物设定、相关前置路径与资产目录，避免每次把整个长剧重写。合并最终 JSON 后必须全剧校验，不把每集通过等同于全剧通过。最终目录仍只保留 `剧情协议.json`。

## 局部修改

在临时目录保留旧文件副本，最终只写修订后的 `剧情协议.json`。允许范围用稳定 key 和字段说明，未涉及内容不得重写。用户只让改台词时，不借机增删单元以修复预算；提出所需调整。共享资产变更需在回复中报告所有引用方和需要重新审核的范围。

## 错误处理

- COUNT/REQUEST/BUDGET：对照展开计划调整授权范围，或向用户说明不可同时满足的约束。
- REFERENCE/OWNERSHIP：补定义或修正引用，不能编造媒体成品。
- CYCLE/UNREACHABLE_ENDING：调整合法分支/条件；保留约定结局并给可行路线。
- SIMULATION_LIMIT：说明覆盖不完整，可在资源允许时显式增大上限或与用户协商简化规则；不得改report为通过。
- MISSING_MEDIA：预期草稿warning，保留需求即可，不尝试自动生成素材。

## 跨模型交接

每次交接提供相同版本的本包、原稿、约束、当前协议 JSON 及最新校验错误。GPT、Grok、DeepSeek 等模型可以任选，不假设产品支持相同工具。不能执行校验时必须声明“未校验”，且不能把文件标为可交付；接收方必须再跑工具。另一个模型复读“没有问题”不能替代确定性测试。
